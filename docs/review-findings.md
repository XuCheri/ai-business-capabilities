## 已修复并独立复验：动作封装对象的访问器可改变工具身份

**组件：** `action-gate`。
**前提：** 宿主向库传入带 JavaScript getter 的 ToolCall 对象；普通解析后的 JSON 不能直接构造 getter。因此，这是本地 API 输入边界问题，不据此声称任何纯 JSON 远程接口均可利用。

初始实现先按 `call.toolId` 读取可信工具，再读取 `call.args`。顶层 args getter 能在后者读取时把 toolId 从只读工具改成破坏性工具。记录随后再次读取变化后的 toolId，却保留旧工具的 read 风险及 allow 状态。工具版本、schema 和主体权限相同时，旧消费逻辑没有要求重新评估为高风险的动作必须持有人审批准，因而能产生破坏性工具许可。

独立复现使用两个仅内存工具 `read` 和 `delete`，没有真实外部动作：

```js
const call = {
  toolId: 'read',
  get args() {
    this.toolId = 'delete';
    return { tenant: 'tenant-a' };
  }
};
```

修复前观测到：预检记录为 `{ toolId: 'delete', risk: 'read', state: 'allow', approvedBy: null }`，随后普通 delete 参数能够消费得到 delete 许可。

**实现修复：**

1. 在读取调用字段前检查完整 ToolCall 的自有属性描述符，只接受明确的 `toolId`、`args` 数据字段，拒绝访问器、符号字段、额外字段及不支持的原型；随后使用固定工具 ID 快照。
2. 消费阶段重新评估结果为 `approval-required` 时，要求记录状态确为 `approved`，不能使用直接 allow 记录替代人工审批。

**独立复验实际结果：**

- preflight 与 consume 对原 getter 复现均返回 `INVALID_CALL`，getter 调用次数为 0。
- 被拒绝的预检没有留下动作记录。
- 普通 read 许可被换成 delete 调用时返回 `APPROVAL_NEEDED`。
- 拒绝错误消费后，原 read 许可仍为 allow，并可按原参数正常消费。

该复验直接导入修复后的 `action-gate/dist/index.js`。实现测试集中也新增了访问器回归用例。以上证明此具体复现被修复，不是针对所有 JavaScript Proxy、宿主集成方式或分布式部署的安全证明。

## 演示页静态审查发现

### action-gate：审批可见草稿可能与待批内容不同（已修复）

静态控制流显示，初版演示预检邮件 A 后，修改左侧草稿为 B 仍能调用 `approve(currentId)` 批准原 A；右侧预检预览隐藏正文，审核人唯一可见的正文可能是 B。核心参数绑定本身正确，但审批界面未显式处理草稿与权威预检内容的差异，容易让人误解当前批准对象。

修复后演示保留预检时的完整规范化调用快照；批准前发现草稿变化时以 `DRAFT_CHANGED` 阻止批准并提示重新预检或恢复原始内容。切换场景、重置会清理快照，重新预检会更新快照。同时保留“已批准后改参再消费”的负向演示。

独立核验直接从最终 `demo/main.js` 提取实际注册的 preflight / approve handler，在 Node VM 中注入真实 `ActionGate` 与真实演示配置执行，结果为：

- A 预检后把正文改为 B，批准抛出 `DRAFT_CHANGED`，原请求仍待审批，审计没有产生 approved 条目。
- 恢复 A 并仅调整 JSON 对象键顺序，能够正常批准，不会把无语义变化的键顺序误判为改参。
- B 重新预检生成新请求后，可批准新的 B 内容。

这是事件处理逻辑级 probe，未使用或冒称浏览器 DOM 验证。根代理随后完成真实浏览器复验：刷新页面 → 邮件预检 → 修改参数 → 批准，返回 `DRAFT_CHANGED`，AG-0001 仍待审批且尚未批准；重新预检修改后的参数，再批准成功。截图已更新。该项已完成逻辑与真实交互两层修复验证。

### evidence-trace：锚点错误被误分到时效检查（已修复）

初版演示使用包含 `VALID` 的宽泛正则筛选时效发现，该片段也能匹配 `ANCHOR_INVALID`，从而把无效原文位置展示成时效问题。现有 7 个固定演示场景没有触发该情况；此项是扩展场景中的展示分类问题，不影响领域决策。

根代理已改为明确的 5 个文档/版本时效错误码列表，并完成 `npm run demo:build` 与 `node --check`。独立复验读取最终源码中的实际筛选表达式执行：5 个时效码全部选中，`ANCHOR_INVALID`、`ANCHOR_MISMATCH`、`QUOTE_NOT_FOUND` 均不再被归入时效检查；旧宽泛正则已不存在。该项已修复，未重复全套领域测试。

## 已提出的可信输入与文案边界

### evidence-trace

- `requiresCitation` 决定一条声明是否必须附证据，不能把模型自行输出的 false 当作业务豁免。当前库允许明确的非必引声明无引用通过；正式服务应由可信业务策略填入此字段。
- `exportAudit` 是普通 JSON 序列化，不会再净化任意传入对象。来源内容过滤来自 `auditAnswer` 输出；导出流程应只传该结果，不能直接传原始 AuditRequest。
- 完整来源注册表先做结构预检，之后按租户与 allowlist 限定引用解析和输出。注册表、身份和 allowlist 必须来自可信服务端；本地函数本身不执行身份认证。
- UTF-16 半开区间精确匹配是自有协议。引用定位正确、数字标记存在不代表语义支持或现实事实正确；代码与测试需要保留明确的反例。

### action-gate

- 风险来自可信工具注册表，不采信模型自报或不可信 MCP annotations。当前 schema 是自定义有限子集，不是完整 JSON Schema 或 MCP 协议验证器。
- 主体、角色、租户、审批者以及业务时钟由宿主提供；库不能把前端字符串变成可信身份。
- 一次性消费的原子性限于同一 JavaScript 实例，不能据此声称跨进程/跨实例 exactly-once。消费成功表示许可已消费，不表示真实工具已经成功执行。
- inspect、list、audit、replacePolicy 面向可信宿主代码，不包含传输层访问控制。生产适配器仍需唯一执行入口、持久化原子消费与下游授权。
